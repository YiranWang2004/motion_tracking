耗时 21秒



不是直接把 MuJoCo 窗口放进 G1_NET=enx6c1ff770ecdd bash scripts/run_bridge.sh 里启动。
这个脚本的职责只有一件事：启动 C++ G1 bridge，并通过 G1_NET 指定 Unitree DDS 使用的网卡：
G1_NET=enx6c1ff770ecdd bash scripts/run_bridge.sh
它会负责：
- 读取 G1 的 rt/lowstate；
- 接收 Python 控制器发到 UDP 55002 的电机命令；
- 发布实时关节状态到 UDP 55001；
- 复制一份只读状态到 UDP 55003，供查看器使用。
它不会启动 Python、OpenVR、MuJoCo viewer，也不会自动读取 Tracker。当前配置中这一点很明确：
state_port: 55001
state_mirror_port: 55003
state_mirror_host: "127.0.0.1"
更合理的进程关系应该是：
g1_udp_bridge
    ├── UDP 55001：给 deploy_omnicontact 读取实机状态
    └── UDP 55003：给孪生 viewer 读取实机关节/IMU状态

deploy_omnicontact
    ├── 读取 Tracker 位姿
    ├── 运行策略
    ├── 发送电机命令到 bridge:55002
    └── 发送 reference/ghost 可视化数据到 viewer

real twin viewer
    ├── 读取 UDP 55003 的真实关节状态
    ├── 读取 Tracker 的 pelvis/box 位姿
    └── 读取 deploy 发来的 ghost/reference 数据
因此建议的启动顺序是：
# 终端 1：启动 bridge
cd /home/bcj/wyr/motion_tracking/g1_sim2real
G1_NET=enx6c1ff770ecdd bash scripts/run_bridge.sh
# 终端 2：启动孪生窗口
cd /home/bcj/wyr/motion_tracking/sim2real
# 未来的 real_omnicontact_viewer.py
uv run --extra vive python scripts/real_omnicontact_viewer.py \
  --vive-config config/g1/omnicontact_vive.json \
  --state-port 55003
# 终端 3：启动 sim2real 控制器
cd /home/bcj/wyr/motion_tracking/sim2real
uv run --extra vive python src/deploy_omnicontact.py \
  --robot g1 \
  --pose-source local \
  --vive-config config/g1/omnicontact_vive.json \
  --act \
  --confirm-actuation ENABLE_MOTORS
viewer 可以在 bridge 之后启动，也可以先启动后等待数据；但它应该是独立进程，不应该运行在 C++ bridge 的实时线程里。原因是 MuJoCo GUI、OpenVR 和 Python 调度都可能阻塞或产生调度抖动，不能影响 1 kHz DDS/电机控制和 200 ms command watchdog。
目前仓库里的 [view_calibrated_omnicontact_poses.py (line 1)](/home/bcj/wyr/motion_tracking/sim2real/scripts/view_calibrated_omnicontact_poses.py:1) 可以作为这个窗口的基础，但它还不是完整的目标版本。它目前能：
- 读 Tracker；
- 用 Tracker 更新 pelvis 和 box；
- 通过 --state-port 55001 叠加实机关节；
但不能接收 deploy_omnicontact 产生的 sim2sim reference/ghost 轨迹。
要完成你描述的功能，还需要增加一条独立的“可视化数据通道”：
1. deploy_omnicontact 在 local/udp 模式下也发送 ReferenceVisualization；
2. 发送目标不能依赖电机命令 UDP，最好使用独立的只读 UDP 端口，例如 55004；
3. 孪生 viewer 同时订阅：
   - bridge 状态镜像 55003；
   - Tracker 位姿；
   - reference/ghost 可视化包 55004；
4. viewer 在与 sim2sim 相同的 XML 中分别显示：
   - 实际机器人；
   - 实际箱子；
   - sim2sim reference；
   - ghost robot；
   - ghost box；
   - 接触状态和起终点平面。
如果 viewer 与 bridge 不在同一台机器上，还需要把 state_mirror_host 从 127.0.0.1 改成 viewer 所在机器的 IP，并让 viewer 绑定对应网卡。G1_NET 只决定 DDS 网卡，不决定 viewer 的网络地址。
所以结论是：启动时可以把 bridge、viewer、deploy 编排成一个统一启动流程，但窗口本身不应该由 run_bridge.sh 直接启动；它应该作为独立 viewer 与 bridge 同步运行。
